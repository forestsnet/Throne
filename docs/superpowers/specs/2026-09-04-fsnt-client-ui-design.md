# FSNT Client: потребительский интерфейс поверх ядра Throne

**Дата:** 04.09.2026
**Ветка:** `sync-upstream-2026-09`
**Статус:** дизайн на согласовании

## Задача

Текущий интерфейс Throne рассчитан на инженера: вкладки групп, таблица профилей с пятью колонками, логи, графики, цепочки, extra core, тесты. Для конечного клиента VPN это избыточно. Нужен простой экран: выбрать сервер, нажать кнопку, видеть остаток трафика.

Инженерный интерфейс при этом никуда не девается — он остаётся расширенным режимом.

## Решения, принятые до дизайна

| Вопрос | Решение | Следствие |
|---|---|---|
| Судьба старого окна | Новое по умолчанию, старое — «Расширенный режим» | Ничего не теряется, синхронизация с upstream остаётся одной операцией |
| Подписки | Несколько наравне | Слева нужен переключатель подписок, список серверов плоский |
| Режим подключения | Одна кнопка, TUN по умолчанию | Выбор режима уезжает в настройки |
| Размещение | Тот же репозиторий и бинарь | Оба окна линкуются с одним ядром |
| Технология | Qt Widgets + делегаты + QSS | См. ниже — QML отпал по инфраструктурной причине |

### Почему не QML

Изначально выбрали QML. Проверка сборочной инфраструктуры это отменила: Windows-сборка берёт Qt из `throneproj/buildqt`, и его скрипт (`buildqt.bat`) собирает ровно четыре модуля — `qtbase`, `qttools`, `qttranslations`, `qtsvg`. Модуля `qtdeclarative` там нет, то есть **QML под Windows текущим CI не собрать вообще**. Сборка вдобавок статическая, а статический QML требует отдельной возни с регистрацией модулей и `qmlimportscanner`.

Варианты «свой билд Qt» и «отказ от статики» остаются открытыми, но каждый — самостоятельный инфраструктурный проект. Widgets не требуют в сборке ни одного изменения.

## Архитектура

### Выбор окна при старте

Единственная точка создания окна — `UI_InitMainWindow()` (`src/ui/mainWindow/mainwindow_setup.cpp:74`), сейчас там `mainwindow = new MainWindow;`. Туда добавляется развилка по новой настройке `ui_mode`:

```cpp
void UI_InitMainWindow() {
    if (Configs::dataManager->settingsRepo->ui_mode == Configs::UiMode::Simple) {
        simpleWindow = new FsntWindow;
    } else {
        mainwindow = new MainWindow;
    }
}
```

Переключение режима требует перезапуска приложения — оба окна держат подписки на одни и те же сигналы ядра, и держать их одновременно значит удваивать обработчики. Перезапуск делается уже существующим механизмом `ExitReason::Restart`.

**Дефолт для новых установок — простой режим. Существующие установки остаются в расширенном:** у текущих пользователей форка интерфейс не должен смениться под ногами после обновления. Различение — по наличию записи `ui_mode` в базе.

### Что переиспользуется без изменений

Новое окно не дублирует логику. Оно потребитель существующего ядра:

| Нужно окну | Откуда берётся |
|---|---|
| Список серверов | `ProfilesRepo`, модель `ProfilesTableModel` |
| Группы подписок | `GroupsRepo` |
| Запуск и остановка | `profile_start` / `profile_stop` |
| Состояние подключения | `settingsRepo->started_id`, `core_running` |
| Пинг серверов | `TestRunner`, поле `latency` профиля |
| Трафик | `TrafficStatsManager` |
| Политика провайдера | `Subscription::ProviderPolicy` |
| Палитра | `ThemeTokens` из `ThemeManager` |

Часть этой логики сейчас живёт методами `MainWindow`. Там, где новое окно должна вызывать те же действия, логика выносится в свободные функции или в отдельный контроллер — дублировать её во втором окне нельзя.

## Компоновка

Окно делится на две панели.

**Левая — выбор сервера:**
- Переключатель подписок: выпадающий список, а не вкладки. Подписок бывает десяток, вкладки разъезжаются.
- Поиск по имени.
- Переключатель «Все / Избранное».
- Список серверов: имя, пинг, значок избранного. Строка «Авто · самый быстрый» первой.

**Правая — состояние и подписка:**
- Таймер подключения и строка состояния.
- Круглая кнопка подключения.
- Текущий сервер.
- Карточка подписки: полоса трафика, дата истечения, дата сброса трафика, ссылки поддержки.

**Шапка:** значок FN, название, шестерёнка настроек, кнопки окна.

Чего в окне нет намеренно: логов, графиков соединений, цепочек, extra core, ручных тестов, правил маршрутизации. Всё это доступно в расширенном режиме.

## Данные карточки подписки

Заголовок `subscription-userinfo` сейчас сохраняется сырой строкой в `group->info` (`GroupUpdater.cpp:260`). Для карточки его нужно разобрать:

```
subscription-userinfo: upload=0; download=0; total=5368709120000; expire=0
```

Вводится разбор в структуру:

```cpp
struct SubscriptionUsage {
    qint64 upload = 0;
    qint64 download = 0;
    qint64 total = 0;      // 0 = безлимит
    qint64 expire = 0;     // 0 = бессрочно
    bool valid = false;
};
SubscriptionUsage ParseSubscriptionUserInfo(const QString &raw);
```

Правила отображения:

- **Трафик.** Полоса заполнения `(upload + download) / total`. При `total = 0` полоса не показывается, вместо неё «Безлимитно».
- **Срок действия.** Скрывается в двух случаях: `expire = 0` и год даты больше 2100. Оба означают «бессрочно»; провайдеры пользуются и тем, и другим. У подписки владельца сейчас именно `expire=0`.
- **Сброс трафика.** Берётся `subscription-refill-date` из политики провайдера. Показывается как дата и относительный срок: «Сброс трафика: 6 марта, через 12 дней». Периодичности в протоколе нет — ни в заголовках Happ, ни у панели владельца, — поэтому «раз в 30 дней» показать неоткуда и обещать этого не будем.
- **Поддержка.** Ссылки `support-url` и `profile-web-page-url` из политики, строкой со значком внутри карточки. В настройки не дублируются: они относятся к провайдеру, а не к клиенту.

## Подключение одной кнопкой

Кнопка не спрашивает режим. Поведение:

1. Если профиль не выбран — берётся первый из текущей подписки, при пустой подписке кнопка неактивна с подсказкой «Добавьте подписку».
2. Режим берётся из настройки `simple_mode_transport`, по умолчанию TUN.
3. При TUN и отсутствии прав вызывается существующий `get_elevated_permissions()`. Его апстримная реализация уже спрашивает пользователя и корректно переживает отказ.
4. Отказ в правах не оставляет кнопку в состоянии «подключается»: состояние возвращается в «отключено» с пояснением.

Выбор транспорта (TUN или системный прокси) присутствует в настройках простого режима — для тех, кому TUN не подходит.

## Брендинг

- Название приложения в простом режиме: **FSNT Client**.
- Значок **FN** в шапке и иконка приложения — предоставляет владелец. До этого момента используется существующая иконка Throne, места под замену подготовлены: `res/Throne.icns` (macOS), `WIN32_EXECUTABLE` (Windows), `res/public/` (значки состояний в трее).
- Фирменный цвет задаётся одним токеном в `FsntTheme` и не размазывается по коду.
- Строка `software_name` в простом режиме — «FSNT Client», в расширенном остаётся текущая с версией и меткой форка.

## Обработка ошибок

- Подписка не обновлялась ни разу: карточка показывает «Нет данных о трафике», полоса скрыта.
- `subscription-userinfo` неразбираем: поля считаются нулевыми, в лог пишется предупреждение, карточка показывает только имя подписки.
- Профиль удалён под ногами (обновление подписки): выбор сбрасывается на первый доступный, подключение не рвётся, если работающий профиль уцелел.
- Подписок нет вовсе: левая панель показывает приглашение добавить подписку, кнопка неактивна.

## Проверка

Собственного тест-сьюта в проекте нет, кроме заведённого нами `ProviderPolicyTest`. Соответственно:

- **Тестами покрывается** разбор `subscription-userinfo` — чистая функция: безлимит, ноль, год больше 2100, мусор на входе, переполнение.
- **Сборкой** — что оба окна компилируются и приложение стартует в обоих режимах.
- **Вручную** — всё остальное: вид, переключение подписок, поиск, избранное, подключение, отказ в правах.

## Разбиение на приросты

Один дизайн, но реализация по частям — каждая даёт работающий результат:

1. ~~**Каркас и тема.**~~ **Готово 04.09.2026.** Настройка `ui_mode`, развилка в `UI_InitMainWindow`, окно с шапкой и двумя панелями, QSS поверх `ThemeTokens`, переходы в обе стороны. Панели пока с заглушками.
2. **Экран подключения.** Кнопка, таймер, состояние, текущий сервер, логика одной кнопки с TUN. Результат: из нового окна можно подключиться и отключиться.
3. **Список серверов.** Делегат строки, поиск, переключатель подписок, избранное с миграцией поля. Результат: сервер выбирается и подключается.
4. **Карточка подписки.** Разбор `subscription-userinfo`, трафик, срок, сброс, ссылки поддержки. Результат: пользователь видит остаток трафика.
5. **Настройки простого режима.** Транспорт, язык, автозапуск, переход в расширенный режим.

Порядок обязателен: каждый следующий прирост опирается на предыдущий.

## Риски

1. **Логика в методах `MainWindow`.** Часть действий (запуск профиля, смена режима, обновление подписки) — методы существующего окна. Их вынос ради переиспользования затрагивает файлы, которые правит upstream, и добавит конфликтов при следующей синхронизации. Смягчение: выносить минимум, оставляя апстримные сигнатуры на месте.
2. **Два окна — два набора подписок на сигналы.** Именно поэтому режим переключается через перезапуск, а не на лету.
3. **Иконки нет.** До получения FN-значка простой режим будет носить иконку Throne. Это видно пользователю, но не блокирует работу.
4. **Избранное — новое поле.** Обновление добавит колонку; откат к предыдущей версии клиента её проигнорирует, данные не пострадают.

## Уточнения, установленные при реализации каркаса

Две вещи выяснились только на запуске и обязательны для следующих приростов.

**Ядро вызывает окно обратно.** В `include/global/Utils.hpp` объявлены четыре глобальные `std::function`: `MW_show_log`, `MW_dialog_message`, `MW_handle_deeplink`, `MW_import_files`. `MainWindow` регистрирует их в своём конструкторе, и ядро зовёт их отовсюду. Окно, которое стартует, обязано их зарегистрировать — иначе первый же вызов падает с `std::bad_function_call`. В каркасе реализации минимальные: логи уходят в `Logging::WriteUserLog`, остальные пишут отладочную строку. Приросты 2-4 наполняют их по мере надобности — особенно `MW_dialog_message`, через который ядро сообщает о смене состояния подключения.

**Тема применяется тем окном, которое стартует.** `themeManager()->ApplyTheme()` вызывается из конструктора `MainWindow` (`mainwindow_setup.cpp:177`). Без такого же вызова в `FsntWindow` палитра остаётся пустой, `ThemeTokens` содержат неинициализированные `QColor`, и окно рисуется чёрным.

Обе зависимости — следствие того, что `MainWindow` исторически совмещает роль окна и роль точки инициализации приложения. Разделять это в рамках интерфейсной работы не стоит: слишком велик риск конфликтов с upstream. Достаточно помнить, что новое окно обязано выполнить те же инициализации.
