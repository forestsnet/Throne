# Политика провайдера: заголовки подписки, сокрытие UI, DNS и per-app прокси

**Дата:** 04.09.2026
**Ветка:** `sync-upstream-2026-09`
**Статус:** дизайн на согласовании

## Задача

Панели экосистемы Happ передают клиенту настройки не в теле подписки, а в **HTTP-заголовках ответа**. Throne сегодня читает из них ровно один — `Subscription-UserInfo`. Нужно научиться разбирать остальные и применять.

Разбор JSON-конфигураций с маршрутизацией в задачу **не входит: он уже работает.** Формат `configJsonArray` (массив полных конфигов Xray) распознаётся, каждый элемент сохраняется как профиль `CustomXrayFullConfig` и выполняется ядром verbatim вместе со своими `routing`, `dns` и балансировщиками. Проверено на реальном ответе `vflex.ru` (486 КБ, 23 элемента, 17 правил маршрутизации в первом). Эта поддержка появилась в upstream после февральской точки расхождения и приехала с синхронизацией.

## Решения, принятые до дизайна

| Вопрос | Решение | Следствие |
|---|---|---|
| Модель доверия | **Сервер диктует всегда** | Пользовательские правки затрагиваемых настроек затираются при обновлении подписки |
| Чьи заголовки главные при нескольких подписках | **Группы активного профиля** | Политику надо хранить у группы и применять в момент активации, а не в момент загрузки |
| Состав заголовков | **Все**, включая управляющие и мобильные | Четыре подсистемы вместо одной |
| Разбиение на подпроекты | **Не разбивать** | Один документ; секции сделаны раздельными, чтобы реализовывать по частям |

## Архитектура

### Политика как единый объект

Заголовки разбираются в объект `ProviderPolicy` и сохраняются **целиком, JSON-ом, в одной новой колонке** `provider_policy_json` таблицы `groups`.

Это принятый в кодовой базе приём: `column_width_json`, `profiles_json`, `process_name_json` — все составные данные лежат JSON-ом в TEXT. Причина именно здесь содержательная: **набор заголовков принадлежит вендору панели, а не нам**, и будет расти. Блоб принимает новые ключи без миграции клиента, а политика всегда читается целиком — выборка по отдельному полю не нужна ни в одном сценарии.

Отвергнутые варианты: колонка на заголовок (каждый новый заголовок панели = миграция клиента, гарантированное отставание) и отдельная таблица ключ-значение (лишняя машинерия и join ради двух десятков ключей, всегда читаемых вместе).

### Трёхзначность: «не прислан» ≠ «false»

Каждый управляющий заголовок хранится как `std::optional<bool>`. Отсутствие заголовка — это отсутствие мнения, а не запрет. Без этого различия панель, однажды не приславшая `tun-enable`, выключала бы пользователю TUN при каждом автообновлении.

Из этого следуют **два разных правила применения**, и это ключевая деталь дизайна:

- **Пользовательские настройки** (`tun-enable`, `subscription-always-hwid-enable`, `subscription-auto-update-enable`): заголовок отсутствует — **не трогаем**. Настройка сохраняет текущее значение.
- **Ограничения интерфейса** (`hide-settings`, `hide-url`, `subscription-pin`, `subscriptions-collapse`): заголовок отсутствует — **ограничение снято**. Ограничение действует только пока активен профиль группы, которая его требует.

Асимметрия намеренная. Если бы ограничения тоже «залипали» при отсутствии заголовка, пользователь, один раз подключившийся к панели с `hide-settings: true`, остался бы с заблокированным интерфейсом навсегда — включая невозможность удалить эту подписку.

### Активная политика

Единая точка доступа:

```cpp
// include/configs/sub/ProviderPolicy.hpp
namespace Subscription {
    // Политика группы, которой принадлежит запущенный профиль.
    // Пустая, если профиль не запущен или его группа политики не имеет.
    const ProviderPolicy &ActiveProviderPolicy();
}
```

На неё смотрят все четыре подсистемы. Пересчитывается в двух точках: при старте профиля (`profile_start`) и при остановке (`profile_stop`) — на остановке становится пустой, что автоматически снимает все ограничения интерфейса.

## Модель данных

```cpp
struct ProviderPolicy {
    int schema = 1;                      // версия формата внутри блоба

    // Информационные
    QString title;                       // profile-title, декодирован из base64:
    QString announce;                    // announce, декодирован из base64:
    QString supportUrl;                  // support-url
    QString webPageUrl;                  // profile-web-page-url
    QString providerId;                  // providerid
    qint64  refillDate = 0;              // subscription-refill-date, epoch
    int     updateIntervalHours = 0;     // profile-update-interval, 0 = не прислан

    // Управляющие, трёхзначные
    std::optional<bool> tunEnable;       // tun-enable
    std::optional<bool> alwaysHwid;      // subscription-always-hwid-enable
    std::optional<bool> autoUpdate;      // subscription-auto-update-enable
    std::optional<bool> dnsFromJson;     // dns-from-json-enable
    std::optional<bool> hideSettings;    // hide-settings
    std::optional<bool> hideUrl;         // hide-url
    std::optional<bool> pin;             // subscription-pin
    std::optional<bool> collapse;        // subscriptions-collapse
    std::optional<bool> pingOnOpen;      // subscription-ping-onopen-enabled

    QString perAppProxyList;             // per-app-proxy-list, формат неизвестен
    QJsonObject unknown;                 // всё нераспознанное, чтобы не терять
};
```

Поле `unknown` — сознательное решение: заголовки, которых мы ещё не знаем, сохраняются и видны в отладочном архиве. Это превращает появление нового заголовка панели из «клиент молча его игнорирует» в «видно, что пришло».

### Миграция

По принятому в проекте образцу (`GroupsRepo.cpp:45`, `RoutesRepo.cpp:32-44`):

```cpp
db.exec("ALTER TABLE groups ADD COLUMN provider_policy_json TEXT NOT NULL DEFAULT ''");
```

Пустая строка = политики нет. Существующие базы мигрируют без потерь, откат к предыдущей версии клиента безопасен — лишняя колонка игнорируется.

## Подсистема 1: разбор и применение заголовков

**Файлы:** новый `src/configs/sub/ProviderPolicy.cpp` + заголовок; правки `GroupUpdater.cpp` (сохранение), `mainwindow_profile_lifecycle.cpp` (применение).

Разбор — рядом с существующим чтением `Subscription-UserInfo` в `GroupUpdater::fetch` (`GroupUpdater.cpp:257`), там уже есть доступ к `resp.header`. Значения с префиксом `base64:` декодируются; при неудаче декодирования берётся сырая строка.

Применение — в `profile_start`, после проверки конфликтующих процессов и до сборки конфига:

| Заголовок | Действие |
|---|---|
| `tun-enable` | `set_spmode_vpn(value, true)` |
| `subscription-always-hwid-enable` | `settingsRepo->sub_send_hwid = value` |
| `subscription-auto-update-enable` | `group->skip_auto_update = !value` |
| `profile-title` | `group->name = title` при обновлении подписки |
| `profile-update-interval` | `settingsRepo->sub_auto_update = hours * 60` |
| `announce`, `support-url`, `profile-web-page-url`, `subscription-refill-date` | показ в свойствах группы |

### Защита от рекурсии

`set_spmode_vpn` заканчивается вызовом `profile_start`, поэтому применение политики внутри `profile_start` зациклилось бы: политика включает TUN, TUN перезапускает профиль, перезапуск снова применяет политику.

Решение — флаг-страж в `MainWindow`:

```cpp
bool m_applyingProviderPolicy = false;

void MainWindow::applyProviderPolicy(int gid) {
    if (m_applyingProviderPolicy) return;   // повторный вход из set_spmode_vpn
    m_applyingProviderPolicy = true;
    // ... применение
    m_applyingProviderPolicy = false;
}
```

Вызов ставится в начало `profile_start`, сразу после проверки конфликтующих процессов. Изменение `tun-enable` при этом по-прежнему перезапускает профиль — это штатное поведение `set_spmode_vpn`, — но политика за одну активацию применяется ровно один раз.

**Приёмка:** подписка с `tun-enable: true` включает TUN при активации своего профиля; подписка без этого заголовка ничего не меняет; `profile-title` переименовывает группу; `announce` виден в свойствах.

## Подсистема 2: ограничения интерфейса

**Файлы:** новый `src/ui/setting/PolicyGate.cpp` + заголовок; правки `dialog_basic_settings.cpp`, `dialog_edit_group.cpp`, `mainwindow_groups.cpp`, `GroupItem.cpp`, `mainwindow_setup.cpp`.

Механизма блокировки UI в проекте нет — `preventModifications` у профиля маршрутизации относится к генерации конфига, а не к интерфейсу. Создаётся новый.

`PolicyGate` — тонкий слой с тремя запросами: `settingsHidden()`, `urlHidden()`, `deletionBlocked(groupId)`. Точки применения:

- **`hide-settings`** — вкладки `tab_2`…`tab_5` и `tab_misc` в `dialog_basic_settings.ui` скрываются через `QTabWidget::removeTab`. Вкладка `tab_1` (базовое) и `tab_backup` остаются: пользователь должен сохранять возможность видеть, что происходит, и сделать резервную копию.
- **`hide-url`** — поле URL в `dialog_edit_group.cpp:30` переводится в режим только-чтение с маскированием.
- **`subscription-pin`** — удаление блокируется во всех трёх точках: `mainwindow_setup.cpp:922`, `mainwindow_groups.cpp:163`, `GroupItem.cpp:131`. Все три обязательны, иначе запрет обходится через другое меню.
- **`subscriptions-collapse`** — группы сворачиваются в `refresh_groups` (`mainwindow_groups.cpp:64`).

**Граница, которую не переходим:** ограничения снимаются при остановке профиля и никогда не переживают перезапуск приложения без активного профиля этой группы. Пользователь всегда может выйти из-под ограничений, остановив профиль. Это защита от невосстановимого состояния.

**Приёмка:** при активном профиле группы с `hide-settings: true` соответствующие вкладки отсутствуют; после остановки профиля возвращаются; удаление закреплённой подписки невозможно ни через одно из трёх меню.

## Подсистема 3: DNS из JSON

**Файл:** правка `src/configs/generate.cpp` (ветка `CustomXrayFullConfig`, около строки 2359).

Там уже вырезается `inbounds` — Throne подставляет свой bridge-inbound. По тому же принципу, при `dnsFromJson == false`, вырезается `dns`:

```cpp
xrayConf.remove("inbounds");
if (Subscription::ActiveProviderPolicy().dnsFromJson == false) xrayConf.remove("dns");
```

Тогда разрешение имён выполняется настройками самого Throne, а не блоком из конфига провайдера.

**Приёмка:** с `dns-from-json-enable: false` в переданном ядру конфиге блока `dns` нет; с `true` или без заголовка — есть.

## Подсистема 4: per-app прокси

**Файлы:** новый `src/ui/setting/dialog_per_app_proxy.cpp` + `.ui`; правка меню маршрутизации.

Механизм уже есть целиком: правила по процессам хранятся в `route_rules` (`process_name`, `process_path`, `process_path_regex`), применяются ядром и разбираются простыми правилами — `RouteProfile.cpp:802` выводит `processName:`, `:908` разбирает, `:937` валидирует. Не хватает только выбора приложений вместо ручного ввода имени процесса.

Диалог показывает список запущенных процессов (`ps` на macOS/Linux, `tasklist` на Windows — тот же способ, что уже используется в `mainwindow_conflicts.cpp`), пользователь отмечает приложения и выбирает для них действие: прокси или обход. Выбор пишется строками `processName:<имя>` в простые правила активного профиля маршрутизации через `UpdateSimpleRules`.

**Приёмка:** отмеченное приложение появляется строкой `processName:` в правилах профиля маршрутизации и учитывается ядром после перезапуска профиля.

## Обработка ошибок

- Некорректный base64 в `profile-title` / `announce` — берётся сырая строка, в лог пишется предупреждение. Подписка не отвергается.
- Нечисловой `profile-update-interval` — заголовок игнорируется, интервал не меняется.
- Повреждённый `provider_policy_json` в базе — политика считается пустой, все ограничения сняты, в лог пишется ошибка. Безопасный отказ: пользователь не остаётся с заблокированным интерфейсом из-за битой строки.
- Неизвестные заголовки — попадают в `unknown`, ни на что не влияют.

## Проверка

Собственного тест-сьюта в проекте нет (тесты только у вендоренного `3rdparty/simple-protobuf`), поэтому критерии — сборка плюс проверка вручную по разделам «Приёмка» выше.

Для проверки без зависимости от панели предусматривается локальная заглушка: небольшой HTTP-сервер, отдающий сохранённый образец тела с настраиваемым набором заголовков. Это единственный способ проверить трёхзначность и снятие ограничений, не прося провайдера менять настройки.

## Риски и открытые вопросы

1. **Формат `per-app-proxy-list` неизвестен.** В образце значение `0`. Список это или флаг — по одному примеру не определить. До получения реального примера с непустым значением поле хранится строкой и не интерпретируется.
2. **Затирание пользовательских настроек.** Прямое следствие принятой модели «сервер диктует всегда»: правки `tun-enable`, HWID и интервала обновления будут молча теряться при каждом обновлении подписки. Владелец предупреждён и подтвердил решение.
3. **Сокрытие настроек на десктопе.** Пользователь на собственном компьютере перестаёт видеть часть своих настроек. Смягчено тем, что ограничение снимается остановкой профиля и не переживает её.
4. **UA форка.** Панель отдаёт JSON только на известные UA. Наш `Throne/<версия> (FSNT Fork)` содержит суффикс — при точном сравнении на стороне панели правило не сработает, нужно сравнение по префиксу `Throne/`.
5. **Заголовки приходят только при обновлении подписки.** Политика применяется при активации профиля, но пополняется только при запросе к панели. Значит после чистой установки, пока подписка ни разу не обновилась, политики нет и ограничения не действуют. Это приемлемо: первое же обновление всё расставит. Но если панель рассчитывает, что `hide-settings` действует с первого запуска, ожидание не оправдается.

### Отклонения от дизайна выше, с обоснованием

1. **Запросы ограничений живут в `ProviderPolicy`, а не в отдельном `PolicyGate.cpp`.** Это не UI-логика, и держать её рядом с самой политикой цельнее.
2. **Скрываются вкладки Subscription, Core, Security, Miscellaneous.** В дизайне значилось «tab_2…tab_5 и tab_misc», но по факту `tab_2` — это «Style», прятать косметику бессмысленно, а `tab_backup` прятать опасно: пользователь должен сохранять право на резервную копию.
3. **`subscriptions-collapse` не реализован.** Утверждение в дизайне, что он ложится на десктоп, оказалось неверным: группы в Throne — вкладки `QTabWidget`, они уже компактны, сворачивать нечего. Заголовок парсится и хранится, действия под него нет.
4. **DNS вырезается в `generate.cpp` в рабочем пути (около строки 1393), а не в валидации (2359).** В дизайне была указана вторая точка — она лишь проверяет конфиг через `CheckConfig` и на исполнение не влияет.
5. **`per-app-proxy-list` не интерпретируется.** Формат по-прежнему неизвестен; заголовок хранится строкой. Сам диалог выбора приложений от него не зависит и работает как обычная пользовательская функция.

### Что осталось проверить руками

1. Вкладки Subscription/Core/Security/Miscellaneous исчезают при активном профиле группы с `hide-settings: true` и возвращаются после остановки профиля.
2. Ссылка подписки скрыта под маской при `hide-url: true` и **не затирается маской при сохранении** свойств группы.
3. Закреплённую подписку (`subscription-pin: true`) нельзя удалить ни через меню «Delete Group», ни через контекстное меню вкладки, ни из карточки группы; чужую подписку — можно.
4. Диалог «Прокси по приложениям»: выбор пишется правилами `processName:`, а **существующие правила по доменам и IP остаются нетронутыми** — это главный риск диалога.
5. При добавлении подписки исчезает пустая группа по умолчанию и открывается именно добавленная.
